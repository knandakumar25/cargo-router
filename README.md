# cargo-router

> **Autonomous Weather-Aware Cargo Routing Microservice**  
> An event-driven, agentic system that reacts to real-time meteorological data to continuously optimize active supply chain freight paths.

---

## Project Overview

`cargo-router` is a production-grade Spring Boot 3.5 microservice that operates as a fully autonomous routing agent for ground freight shipments. The system ingests cargo events from an Apache Kafka 4.2 topic, persists state through Spring Data JPA into an embedded H2 database, and executes a background agentic loop that continuously monitors every active shipment against live weather conditions sourced from the Open-Meteo REST API.

When a route's assessed risk score crosses a configurable threshold (`general.risk-threshold: 0.65`), the loop generates a ranked set of alternative paths using a `PriorityQueue`-based min-heap, selects the globally optimal route via a weighted composite score function, and publishes a `RerouteCommand` back to Kafka — all within a single, self-contained 60-second decision cycle. Every committed reroute is written to an immutable `RouteDecision` audit record in H2, creating a complete, queryable history of every autonomous action taken by the system.

The architecture mirrors enterprise-grade, event-driven patterns commonly deployed in high-throughput retail logistics pipelines and financial transaction processing systems. It leverages a robust, asynchronous decoupled messaging model utilizing a Kafka `JsonDeserializer` serialization strategy, structured JPA/H2 persistence for transactional consistency, and an isolated `RestTemplate` HTTP client pattern for reliable external service integration.

## Core Features

### Event-Driven Ingestion via Apache Kafka (KRaft Mode)

Inbound `CargoShipment` JSON events are consumed from the `cargo-updates` topic by `ShipmentListener`, which validates each message for a non-null `shipmentId`, `originWarehouse`, and `destinationStore` before any persistence occurs. The consumer is configured with Spring's `JsonDeserializer` targeting `com.logistics.cargorouter.foundation.CargoShipment`, operating within the `cargo-router-group` consumer group. Idempotency is enforced via `ShipmentRepository.existsById()` to silently drop replayed events. Reroute commands are published back to the `reroute-commands` topic via a typed `KafkaTemplate<String, RerouteCommand>`.

### Autonomous Agentic Loop

`AgenticLoop` is annotated with `@Scheduled(fixedDelayString = "${general.agent-interval-ms:60000}")`, executing every 60 seconds on a JDK 25 virtual thread (enabled via `spring.threads.virtual.enabled: true`). Fixed delay prevents cycle overlap; a new cycle begins only after the previous one completes in full. Each execution follows a four-phase protocol:

| Phase | Component | Action |
|---|---|---|
| ① Monitor | `ShipmentRepository` | Load all `ACTIVE` and `REROUTED` shipment records |
| ② Assess | `RiskAssessor` + `WeatherMonitor` | Score the current route by querying live weather for each waypoint |
| ③ Predict | `RouteRanker` | Build a min-heap of alternative routes; extract the global minimum composite cost |
| ④ Act | `RerouteDecider` | Publish `RerouteCommand` to Kafka; persist immutable `RouteDecision` audit record |

### Live Weather Risk Assessment

`WeatherMonitor` queries `https://api.open-meteo.com/v1/forecast` with latitude/longitude coordinates drawn from a static registry of **34 major North American freight hubs** (Chicago, Dallas, Atlanta, Los Angeles, Seattle, New York, Houston, Denver, and 26 others). The WMO weather interpretation code returned by the API is mapped to a base risk score on a continuous `[0.0, 1.0]` scale:

| WMO Code Range | Condition | Base Risk |
|---|---|---|
| ≥ 95 | Thunderstorm / Hail | `0.90` |
| ≥ 85 | Snow Showers | `0.75` |
| ≥ 71 | Heavy Snow | `0.70` |
| ≥ 80 | Rain Showers | `0.50` |
| ≥ 51 | Drizzle / Rain | `0.45` |
| ≥ 45 | Fog | `0.30` |
| < 45 | Clear / Cloudy | `0.05` |

Wind speeds exceeding 80 kph add a continuous penalty of up to `+0.15`. `RiskAssessor` applies a **worst-waypoint-dominates** strategy — a single dangerous leg makes the entire route high-risk, because a truck cannot teleport past a storm corridor regardless of conditions elsewhere on the path. On any API failure the component returns a zero-risk report (fail-open), preserving agent cycle continuity during transient network outages.

### Algorithmic Optimization — Power-of-Two Min-Heap

`RouteRanker` enqueues all alternative paths generated by `ShipmentAggregator` into a `PriorityQueue<RouteCandidate>` — Java's binary min-heap with an internal array that grows at power-of-two boundaries — and extracts the globally optimal route in **O(k log k)** time. Each candidate is ordered by a weighted composite score that balances environmental risk against schedule impact:

$$\text{compositeScore} = \left(\text{weatherRisk} \times 0.70\right) + \left(\frac{\min(\Delta\text{delay}_\text{hrs},\ 24)}{24} \times 0.30\right)$$

Weather safety accounts for 70% of the score; time penalty accounts for 30%. A delay delta of zero or negative (alternative is equally fast or faster than the current route) contributes nothing, meaning shorter routes always dominate at identical risk. `RerouteDecider` applies a minimum improvement gate (`general.min-improvement-threshold: 0.10`) before committing, preventing churn when the best available alternative offers only marginal benefit.

### Explainable AI (XAI) — Persistent Decision Audit Trail

Every committed routing action is persisted as an immutable `RouteDecision` JPA entity in the `route_decision` table. Each record captures: `shipmentId`, `driverId`, `previousRoute`, `newRoute`, `previousRisk`, `newRisk`, a human-readable `trigger` label (e.g. `WEATHER_THUNDERSTORM@CHICAGO`, `WEATHER_HEAVY_SNOW@DENVER`), and a nanosecond-precision `decidedAt` timestamp. This creates a complete, queryable, replay-capable audit log of every autonomous action — exposed at `GET /shipment/{id}/decisions` sorted newest-first.

### Step-by-Step Message Journey

**1. Kafka Ingestion**  
A `CargoShipment` JSON packet arrives on the `cargo-updates` topic (partition `kafka-updates-0`). Spring Kafka's `JsonDeserializer` maps it directly to `com.logistics.cargorouter.foundation.CargoShipment` via the `spring.json.value.default.type` consumer property.

**2. Validation & Persistence**  
`ShipmentListener.listen()` performs null/blank guards on `shipmentId`, `originWarehouse`, and `destinationStore`. If the shipment ID already exists in H2 (`ShipmentRepository.existsById()`), the event is dropped for idempotency. Otherwise, `ShipmentAggregator.buildInitialRoute()` executes a depth-first search over the `SEGMENT_INDEX` corridor graph (21 connected freight hubs) to compute the initial multi-hop route. A `ShipmentRecord` is saved to the `shipment_record` table with status `ACTIVE`.

**3. Agent Cycle Pick-Up**  
Every 60 seconds, `AgenticLoop.cycle()` calls `ShipmentRepository.findByStatus("ACTIVE")` and `findByStatus("REROUTED")` to collect all shipments under active surveillance.

**4. Risk Assessment**  
`RiskAssessor.score()` iterates over every comma-delimited waypoint in `ShipmentRecord.currentRoute`, calling `WeatherMonitor.assess(city)` for each. The highest individual waypoint risk and its `trigger` label are returned as a `RiskAssessor.AssessmentResult` sealed record.

**5. Heap Ranking**  
If the current risk exceeds `0.65`, `RouteRanker.rank()` delegates to `ShipmentAggregator.buildAlternatives()` which generates all first-hop-distinct paths from the origin. Each candidate is inserted into a `PriorityQueue<RouteCandidate>`. A single `heap.poll()` surfaces the globally minimum composite score in O(k log k).

**6. Decision & Audit**  
`RerouteDecider.act()` verifies the improvement gap (`currentRisk - best.getWeatherRisk()`) exceeds `0.10`. If so: a `RerouteCommand` is published to `reroute-commands`; `ShipmentRecord.currentRoute` is updated to the new waypoint string; status transitions to `REROUTED`; and an immutable `RouteDecision` row is written to H2 with the full before/after context.

## Verification & Test Suite

The project ships with **36 JUnit 5 unit tests** across two classes. The entire suite runs with **zero Spring context initialization and zero H2 database connections** — all external dependencies are replaced by Mockito stubs.

### Test Architecture Principles

- **Complete Mockito Isolation** — `ShipmentRepository`, `RiskAssessor`, and `ShipmentAggregator` are all replaced via `@ExtendWith(MockitoExtension.class)`, ensuring no broker, no database, and no HTTP traffic is required.
- **Zero-NPE Defensive Coverage** — Every null, blank, short, and corrupt input path is explicitly exercised via `@NullAndEmptySource`, `@ValueSource`, and `@CsvSource` parameterized annotations.
- **Power-of-Two Heap Boundary Verification** — `RouteRankerTest` drives exactly **1, 2, 4, and 8 candidates** (2⁰ through 2³) through the `PriorityQueue` to assert correct sift-down promotion and global minimum extraction at each internal array resize boundary.
- **Composite Score Arithmetic Precision** — Heap poll results are verified against independently computed `compositeScore` values using `assertThat(...).isCloseTo(..., within(1e-9))`.

## Quick Start Guide

### Prerequisites

- JDK 25 (project uses virtual threads)
- Apache Kafka 4.2 binary distribution — [kafka.apache.org/downloads](https://kafka.apache.org/downloads)
- Maven (or use the included `mvnw` wrapper)

---

### Step 1 — Initialize Kafka KRaft Storage

Before launching the broker, you must generate a cluster ID and format your local storage directory using the standalone KRaft tool.

**On macOS / Linux**

```bash
# Set your Kafka installation directory (adjust to your local path)
export KAFKA_HOME="/usr/local/kafka"

# Generate a fresh cluster UUID
CLUSTER_ID=$($KAFKA_HOME/bin/kafka-storage.sh random-uuid)
echo "Cluster ID: $CLUSTER_ID"

# Format the log directory in standalone KRaft mode
$KAFKA_HOME/bin/kafka-storage.sh format \
    --standalone \
    --config "$KAFKA_HOME/config/kraft/server.properties" \
    --cluster-id "$CLUSTER_ID"
```

**On Windows (PowerShell)**

```powershell
# Set your Kafka installation directory (adjust to your local path)
$KAFKA_HOME = "C:\kafka"

# Generate a fresh cluster UUID
$CLUSTER_ID = & "$KAFKA_HOME\bin\windows\kafka-storage.bat" random-uuid
Write-Host "Cluster ID: $CLUSTER_ID"

# Format the log directory in standalone KRaft mode
& "$KAFKA_HOME\bin\windows\kafka-storage.bat" format `
    --standalone `
    --config "$KAFKA_HOME\config\kraft\server.properties" `
    --cluster-id $CLUSTER_ID
```

---

### Step 2 — Start the Kafka Broker

Launch the unified KRaft broker cluster. Leave this terminal window active to handle the real-time event pipeline.

**On macOS / Linux**

```bash
$KAFKA_HOME/bin/kafka-server-start.sh $KAFKA_HOME/config/kraft/server.properties
```

**On Windows (PowerShell)**

```powershell
& "$KAFKA_HOME\bin\windows\kafka-server-start.bat" "$KAFKA_HOME\config\kraft\server.properties"
```

---

### Step 3 — Create the Required Topics

Open a second terminal window to provision the data channels before booting the application.

**On macOS / Linux**

```bash
$KAFKA_HOME/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic cargo-updates --partitions 1 --replication-factor 1
$KAFKA_HOME/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic reroute-commands --partitions 1 --replication-factor 1
```

**On Windows (PowerShell)**

```powershell
& "$KAFKA_HOME\bin\windows\kafka-topics.bat" --bootstrap-server localhost:9092 --create --topic cargo-updates --partitions 1 --replication-factor 1
& "$KAFKA_HOME\bin\windows\kafka-topics.bat" --bootstrap-server localhost:9092 --create --topic reroute-commands --partitions 1 --replication-factor 1
```

---

### Step 4 — Build and Start the Application

From the root of your `cargo-router` project directory, boot the Spring container:

**On macOS / Linux**

```bash
./mvnw spring-boot:run
```

**On Windows (PowerShell)**

```powershell
.\mvnw spring-boot:run
```

The microservice will boot on port **28500**. Verify baseline liveness by curling the active shipments endpoint: `http://localhost:28500/shipments/active`

---

### Step 5 — Publish a Test Cargo Shipment

Open an interactive console producer to feed a simulated logistics event into your live ingestion topology.

**On macOS / Linux**

```bash
$KAFKA_HOME/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic cargo-updates
```

**On Windows (PowerShell)**

```powershell
& "$KAFKA_HOME\bin\windows\kafka-console-producer.bat" --bootstrap-server localhost:9092 --topic cargo-updates
```

Once the interactive input prompt (`>`) opens, paste this JSON string and press **Enter**:

```json
{
  "shipmentId":       "SHP-2026-00001",
  "originWarehouse":  "d5566b15-b071-4acf-8e8e-c98433083b2d",
  "destinationStore": "50d33715-4c77-4dd9-8b9d-ff1ca372a2a2",
  "driverId":         "DRV-4421",
  "products":         ["lotion", "skis", "bikes"],
  "totalQuantity":    240
}
```

`ShipmentListener` resolves `originWarehouse` → **Chicago** and `destinationStore` → **Nashville** via the `WAYPOINT_CATALOG` UUID prefix lookup, constructs the initial DFS multi-hop route (e.g. `Chicago,Indianapolis,Louisville,Nashville`), and persists a `ShipmentRecord` with status `ACTIVE`. Within the next agent cycle (≤ 60 seconds), `AgenticLoop` will evaluate every waypoint against live Open-Meteo weather data and autonomously reroute if the assessed risk exceeds `0.65`.
